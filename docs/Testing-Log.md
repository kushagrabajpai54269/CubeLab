## Manual Testing
**First round (end of Phase B, before stabilization) — 2026-07-31.** User manually tested the deployed build and reported one functional bug plus six UX findings:
1. **Functional bug** — importing a legal algorithm (`R U R' U'`, "From Solved") produced a false "a corner appears twisted in place" Health Check failure. Reported with an explicit request to investigate root cause before any fix — see D-039 and Development Journal Entry 14 for the full investigation and resolution.
2. Solver navigation didn't lead to the working Health Check page.
3. Cube-net orientation (which face is Front/Up/etc.) wasn't self-explanatory for a first-time user with a physical cube in hand.
4. Dark mode visibly flashed light mode on page refresh.
5. White stickers were hard to distinguish from the page background in light mode.
6. Import/Export workflow wasn't immediately obvious.
7. General request for a first-time-user UX pass.

All seven items were addressed in the stabilization pass (D-039–D-042).

**Second round (after stabilization) — 2026-07-31.** User re-tested the updated build and confirmed all seven items resolved. **Phase B formally accepted on this basis.**

## Edge Cases Tested
Originally planned coverage (from the pre-implementation SRS pass) is now partially executed, tracked here against what's actually been tested:
- ✅ Impossible/illegal cube states (invalid color counts, invalid corner/edge parity, duplicate center colors) — `validator.test.ts`, `validator.legality.test.ts`
- ✅ Legally-reached states being correctly recognized as legal — `validator.legality.test.ts` (this specific edge case is what D-039 was about, and is now the most heavily-covered case in the suite)
- ⚠️ Duplicate sticker color assignment during input — implicitly covered (painting any facelet any color is unrestricted by the UI, and the Validator correctly flags the resulting color-count problem), but no dedicated UI-level test exists
- ✅ Browser refresh mid-edit (state must restore) — `useCubeEditorStore.test.ts`'s hydration tests cover this at the store level; not verified via an actual browser refresh (no UI test harness yet)
- ⬜ Browser close and reopen (same requirement) — not separately tested; same persistence mechanism as the above, so likely covered in practice, but not independently verified
- ⬜ Multiple rapid clicks on Solve — not applicable yet, no Solve button exists (Phase C/D)
- ⬜ Invalid/unknown URLs — not tested
- ⬜ LocalStorage unavailable (private browsing, quota exceeded, disabled by policy) — not tested; `StorageAdapter`'s async interface (D-002) would make this straightforward to test against a failing implementation, but no such test exists yet
- ⬜ Slow network conditions — not tested
- ✅ Invalid/malformed facelet-string and algorithm import (wrong length, bad character, unsupported token, empty input) — `serialization.test.ts`

## Remaining Coverage Gaps
- Integration and UI (component-level) tests remain a complete gap — flagged in Known Issues as increasingly important to close before Phase D's 3D interactions ship.
- Browser-level verification (actual refresh/close-reopen behavior, not just store-level hydration tests) hasn't been done.
- LocalStorage-unavailable and slow-network conditions remain untested.
- `next build` has never been verified end-to-end in the sandbox development environment (network restriction, unrelated to code correctness) — recommend a real build check in the user's own environment before deploying, in addition to the `npm test`/`typecheck`/`lint` checks already run there.
- Large-scale solver correctness fuzzing (scrambled `CubeState` → solver → `applyMoves` → confirmed solved, across thousands of random scrambles) is intentionally not part of Subsystem 0's test suite — there's no stage-specific solving logic yet for it to exercise. This was Subsystem 7 in the approved Phase C plan and remains future work, to be built incrementally alongside Subsystems 1–6 rather than deferred to the end.
