## Failed Tests
- The `validator.legality.test.ts` suite, when first run against the *unfixed* `CORNER_FACELETS` table during the D-039 investigation, failed extensively (this was the diagnostic fuzzing, not the final committed test file — the committed version only exists post-fix and has always passed). Not a "failed test" in the sense of a flaky or incorrect test; this is the record of the test suite doing exactly its job.
- **Phase C, Subsystem 2 (White Cross) exploratory investigation:** a 500-trial randomized fuzz run against an early, unfixed implementation failed at trial 92, revealing a genuine infinite oscillation between two edges — this was diagnostic investigation work (in temporary, since-deleted scratch files, never part of the committed suite), not a failure of any committed test. Root-caused, fixed, and permanently regression-tested with the exact failing scramble — see D-046 and Fixed Issues below. Separately, a follow-up attempt at a larger (10,000-trial) exploratory fuzz run was interrupted mid-edit before it ever executed; no results from it were ever produced or are reported anywhere in this project's documentation.
- **Phase C, Subsystem 3 (First-Layer Corners): two real defects, both caught by the exhaustive single/pair-move suite immediately (not fuzzing) once wired into the full pipeline.** First: `cornerInsertionAlgorithms.ts`'s own self-verifying derivation used a goal test that checked only "target solved", not full preservation — it silently accepted a short "coincidental undo" instead of the genuinely-preserving algorithm, causing a real infinite oscillation between two corners on an early single-move test case. Second, after that fix: a bare `U` turn exposed that the diagonal-slot eject case disturbs a white-cross edge, which the original retry loop had no mechanism to detect or repair. Both root-caused, fixed (D-047, D-048), and permanently regression-tested in the committed suite — see Fixed Issues below.

- **Phase C, Subsystem 4 (Second-Layer Edges): a genuine deterministic cycle, caught by seeded fuzzing (not the exhaustive/regression suite) and confirmed via manual round-by-round tracing.** An eject branch wrongly treated as "forced to one face" (mirroring D-048's corner design) was, once corrected to a genuine 2-way placed-aware choice, still not sufficient — the longer 8-move insertion's higher collateral disturbance made the fixed round-robin order itself hit a real period-4 fixed point. A same-period rotation attempt failed by synchronizing with the cycle instead of breaking it. Fixed with greedy least-collateral-disturbance target selection (D-049). Verified clean across 2000+ seeded trials.
- **Phase C, Subsystem 5 (Last-Layer Orientation): three dead ends during algorithm derivation, all diagnosed by direct construction and real-engine verification rather than theorizing.** A hand-constructed corner-twist fixture wasn't reachable within a practical search depth under the natural `{D, own1, own2}` move set (mirroring D-045's facing-side lesson). A hand-translated "D-for-U" Sune substitution, verified against the real Move Engine per this project's standing rule, was found to disturb last-layer edges (mirroring D-039's chirality lesson). Pure greedy hill-climbing for the corner-orientation round loop converged for only 5 of 27 legal twist patterns — the classic "repeated Sune" plateau. None of these were committed-suite failures; all were caught during derivation/design, before the corresponding code was accepted, and are recorded in full in D-050.

## Fixed Issues
- Phase A: the corner-integrity test-construction helper silent no-op (D-029) — see Testing Log's prior entry, preserved above in Unit Tests Completed's `pieces.test.ts`/`validator.test.ts` description.
- Phase A: two `explainInvalidToken` classifier bugs caught by notation error-message tests (D-028) — see `notation.test.ts` description above.
- **Phase B: the D-039 corner-orientation chirality bug** — found via user manual testing, root-caused via fuzzing (not the single reported example, which misleadingly passed on its own), fixed in the geometry-derivation script, and permanently regression-tested. Full detail in the Decision Log and Development Journal rather than duplicated here.
- Phase B stabilization pass: one self-caught regression before shipping — an intermediate version of `CubeNet`'s face-label positioning hardcoded a 3×3 block size; caught on review and generalized to `cube.size` before it reached the user.
- **Phase C, Subsystem 2: the White Cross "facing side" 2-face assumption** — the original design proposed that D-layer facing-side insertion could be solved using only {own face, D}, same as facing-down. Disproved by full orbit exhaustion before any production code was written (D-045); corrected to use a genuine third face, self-verified against the real Move Engine rather than assumed.
- **Phase C, Subsystem 2: the White Cross edge-oscillation bug** — an early implementation's foreign-face selection had no awareness of which edges were already solved, causing two edges to deterministically re-disturb each other forever on certain scrambles. Found via randomized fuzzing (not the exhaustive single-edge suite, which cannot exercise multi-edge interaction), root-caused by manual trace, and fixed with a placed-aware preference plus a mechanical cycle-detection termination guarantee (D-046). The exact originally-failing scramble is now a permanent regression test in `whiteCross.test.ts`.
- **Phase C, Subsystem 3: the corner-insertion derivation's weak goal test** — `cornerInsertionAlgorithms.ts`'s self-verifying derivation originally checked only that the target corner ended up solved, not that both same-face sibling corners and the full cross remained solved too. Fixed by requiring full preservation in the derivation's own goal test (D-047), the same distinction that mattered for the whole design in the first place.
- **Phase C, Subsystem 3: the diagonal-slot eject cross-disturbance bug** — the one corner-eject case needing a genuine foreign face (the U-layer slot diagonally opposite a corner's home) was found, via a bare `U`-turn test case, to disturb that face's own white-cross edge — and the original retry loop only tracked corners, with no path to repair a disturbed cross edge. Fixed by extending `solveFirstLayerCorners`'s round-robin loop and cycle-detector to track and repair cross-edge state alongside corner state (D-048). The exact `U`/`U2`/`U3` scrambles are now a permanent regression test in `firstLayerCorners.test.ts`.
- **Phase C, Subsystem 3: a slow (~40s) module load** — the derivation's own test-fixture construction originally used an expensive move-based search; switched to direct facelet construction (the same pattern `validator.test.ts`'s own helpers use), bringing load time to ~4s. A performance fix, not a correctness one, but caught one further bug along the way: an initial version of the direct construction used the wrong color for the vacated slot (`solvedColorOf('D')` instead of the target identity's own actual color), producing an unidentifiable corner — caught immediately by the module's own self-verification throwing at load time.
- **Phase C, Subsystem 4: the Second-Layer Edges "forced eject face" assumption and the period-4 round-robin cycle** — an eject branch mirroring D-048's corner design wrongly treated one E-layer branch as forced to a single face; corrected to a genuine placed-aware 2-way choice, which reduced but didn't eliminate a real deterministic cycle. A same-period rotation attempt was tried and failed (it synchronized with the cycle instead of breaking it). Fixed with greedy least-collateral-disturbance target selection, re-evaluated after every move (D-049).
- **Phase C, Subsystem 5: the `dCornerTwist` slot-invariance bug** — a helper meant to detect a D-layer corner's twist state by reusing `pieces.ts`'s `cornerOrientation` directly was found, via direct testing, to register a nonzero "twist" after a single pure D turn (which physically only permutes corners, never twists them) at slots other than a piece's own home slot. Root-caused and removed entirely — replaced with the already-correct, slot-local `isLastLayerCornerOriented` boolean (D-050).
- **Phase C, Subsystem 5: two algorithm-derivation dead ends, corrected before any code was accepted** — a hand-constructed corner-twist test fixture wasn't reachable under the natural 3-generator move set (fixed by switching to forward-search-then-invert, which searches from the known-reachable solved state instead); a hand-translated "D-for-U" Sune substitution was found, via real Move Engine verification, to disturb last-layer edges (fixed the same way). Full account in D-050.
- **Phase C, Subsystem 5: pure greedy corner-orientation convergence failure** — orchestrating the corner-orientation step via pure greedy hill-climbing (always take whichever D-rotation offset most improves the immediate oriented-corner count) converged for only 5 of the 27 possible legal corner-twist patterns. Fixed with a bounded round-level search (branching 4, depth <=8, full-state deduplicated) over which offset to apply each round, which converges all 27/27 (D-050).
